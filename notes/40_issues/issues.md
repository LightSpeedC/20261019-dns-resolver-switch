## 1. 動作確認

### i261019-01 ✅ **済** Windows の nslookup から問い合わせると応答が無い

`nslookup -port=10053 example.org. 127.0.0.1` が「No response from server」になる。サーバのログに問合せが 1 行も出ないので、問合せがサーバに届いていない。`tools/50_run/query.ts` からは UDP・TCP とも届き、解決できる。nslookup が送る先（ポート・アドレス）を調べる。

- ✅ **済** nslookup が実際に送っている宛先を確かめる → 53 番と 10053 番の両方で待ち受けて確かめたところ、`-port=10053` を付けても 53 番にだけ届いた。Windows の nslookup は `-port` を受け付けても送り先を変えない。リゾルバの不具合ではない
- ✅ **済** ポート 53 で起動し、Windows 標準の nslookup から使えるかを確かめる → 127.0.0.1:53 で起動し、UDP（A・AAAA・存在しない名前）と TCP（`-vc`）で正しく返った。53 番の待受けに管理者権限は要らなかった。OS の DNS 設定へ登録するのは利用者が行う

## 2. 応答の中身

### i261019-05 ✅ **済** 切り詰めた応答から EDNS の OPT が落ちる

UDP の上限を超えた応答を TC 付きの質問部だけに作り直すとき、OPT も落ちていた。問合せ元が EDNS 非対応と誤解すると、以後 512 バイトに下がって切り詰めと TCP の取り直しが増える。DO ビットの返事も落ちる。名前が引けなくなることは無い（TCP で取り直すため）。

- ✅ **済** 上流の応答の OPT を写す。上流の応答に OPT が無く、問合せに OPT があれば、自分の OPT（大きさ 1232）を付ける

### i261019-06 ✅ **済** UDP に対応していない上流には TCP だけで問い合わせる

上流によっては UDP に答えず TCP だけで答える。そのような上流へ UDP を送り続けると、毎回 UDP の待ちが無駄になり、その組は primary が返さない扱いになる。

- ✅ **済** 起動時、待ち受けを始める前に、上流ごとに UDP と TCP で確かめる問合せ（`. NS`）を送る。どんな応答（REFUSED 等を含む）でも返れば、その方式は使えるとみなす。UDP が返らず TCP が返る上流は TCP 専用にする。どちらも返らない上流は UDP のまま（落ちているだけかもしれない）とし、WARN を出す
- ✅ **済** 動いている間も、UDP で応答の無い試行が続いた上流（連続 5 回）は確かめ直し、TCP 専用に切り替える。TCP 専用の上流も、定期的に（既定 10 分）UDP を確かめ直し、答えるようになったら戻す
- ✅ **済** 設定で組ごとに `transport` を `auto`（既定・確かめる）／ `udp` ／ `tcp`（決め打ち・確かめない）から選べるようにする
